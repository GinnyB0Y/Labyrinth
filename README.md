# Labyrinth — прототип FPS-игры

Небольшой прототип от первого лица: игрок появляется в процедурно
сгенерированном лабиринте, собирает бриллианты, избегает врагов и
выбирается через выход.

## Как запустить

1. Открыть проект в Unity **6000.2.11f1** (Unity 6).
2. Открыть сцену `Assets/Scenes/Labyrinth.unity`.
3. Нажать **Play**.

Вся геометрия лабиринта, игрок, бриллианты, враги, выход и UI создаются
программно при запуске сцены (см. `GameEntryPoint`), поэтому сцена
содержит только свет и один объект-точку входа — генерация каждый раз
даёт новый случайный лабиринт (если не задан `randomSeed` в инспекторе).

## Управление

| Действие | Клавиша/устройство |
|---|---|
| Движение | `W A S D` |
| Бег (ускорение) | `Shift` (удерживать) |
| Осмотр камерой | Мышь |
| Перезапуск уровня | Кнопка **Restart** на экране победы/поражения |

Курсор блокируется в центре экрана в первом лице и освобождается
автоматически при победе/поражении.

## Цель игры

- Собрать все бриллианты в лабиринте.
- Дойти до зелёной зоны выхода — победа засчитывается только там, и только
  если все бриллианты уже собраны. Само по себе последнее собранное
  сокровище победу не даёт — до выхода ещё нужно дойти.
- Если враг подходит вплотную — поражение.
- На экране победы/поражения игрок и враги замирают: их управление
  и движение отключаются, пока не нажата **Restart**.

## Архитектура

Проект разбит на небольшие классы с одной ответственностью, без единого
"God-объекта". Точка входа — компонент `GameEntryPoint`, который выступает
composition root: генерирует лабиринт, регистрирует общие сервисы в
`ServiceLocator` и делегирует создание всех игровых объектов и UI фабрикам
(`IGameFactory`, `IUIFactory`). Сам он не содержит игровых правил (кто кого
ловит, когда победа и т.п.) — только сборку уровня.

### ServiceLocator + фабрики

- `ServiceLocator` (`Core/ServiceLocator.cs`) — статический реестр сервисов
  (`Register<T>`, `Get<T>`, `TryGet<T>`, `Clear`), хранящий по одному
  экземпляру на тип. `GameEntryPoint` очищает его в начале `Awake()` и
  регистрирует туда `GameSession`, `DiamondCollector`, `IGameFactory` и
  `IUIFactory` — остальные классы получают их через `ServiceLocator.Get<T>()`,
  а не через длинные цепочки параметров. `GameFactory.CreatePlayer(...)`
  дополнительно регистрирует туда `PlayerStamina` в момент создания игрока,
  чтобы `UIFactory` могла достать её при построении полосы стамины.
- `IGameFactory` / `GameFactory` (`Factories/`) — фабрика игровых объектов:
  создаёт игрока, бриллианты, врагов и выход. Сама достаёт `GameSession` и
  `DiamondCollector` из `ServiceLocator`, поэтому `GameEntryPoint` вызывает
  только `gameFactory.CreatePlayer(...)`, `CreateDiamonds(...)`,
  `CreateEnemies(...)`, `CreateExit(...)` — не занимаясь сборкой
  GameObject'ов напрямую.
- `IUIFactory` / `UIFactory` (`UI/`) — то же самое для интерфейса:
  строит Canvas/HUD/панели победы-поражения и связывает их с `UIManager`,
  читая `DiamondCollector`/`GameSession`/`PlayerStamina` из `ServiceLocator`.
- `DiamondFactory` / `EnemyFactory` (`Factories/`) — низкоуровневые
  статические фабрики, которые собирают конкретный GameObject бриллианта
  или врага из примитивов. `GameFactory` использует их как "кирпичики".

### Namespaces / папки (`Assets/Scripts`)

- **`Core/`**
  - `GameEntryPoint` — точка входа/composition root. Генерирует лабиринт
    (`MazeGenerator` + `MazeBuilder`), регистрирует сервисы в
    `ServiceLocator` и делегирует спавн игрока/бриллиантов/врагов/выхода в
    `IGameFactory`, а UI — в `IUIFactory`.
  - `ServiceLocator` — реестр сервисов на время сессии (см. выше).
  - `GameSession` — координатор состояния игры: `Playing / Won / Lost`,
    события `StateChanged`, методы `ReportVictory()`, `ReportDefeat()`,
    `RestartLevel()`. **Здесь находится логика победы/поражения** (в виде
    реакции на события от `ExitZone` и `EnemyAI`, а не как отдельная игровая
    логика — сами условия проверяют они, `GameSession` только фиксирует итог
    и оповещает подписчиков): `ExitZone` вызывает `ReportVictory()` только
    если игрок дошёл до выхода **и** `DiamondCollector.AllCollected` уже
    `true` — сбор последнего бриллианта сам по себе победу не даёт.
    `PlayerMovement`, `PlayerCameraController` и `EnemyAI` получают ссылку
    на `GameSession` через `Initialize(...)` и проверяют `session.IsPlaying` в своём
    `Update()` — как только состояние меняется на `Won`/`Lost`, они
    перестают обрабатывать ввод и движение (враги дополнительно
    останавливают `NavMeshAgent.isStopped = true`).
  - `GameState` — enum состояния игры.

- **`Maze/`**
  - `LabyrinthGenerator` — чистый алгоритм генерации топологии лабиринта
    (recursive backtracker), не создаёт GameObject'ы.
  - `LabyrinthData` — неизменяемые данные о стенах лабиринта.
  - `LabyrinthBuilder` — превращает `LabyrinthData` в геометрию сцены (пол и
    стены из примитивов Cube).
  - `CellPicker` — вспомогательный класс: выбирает случайный набор клеток
    лабиринта без повторов (используется и `GameEntryPoint`, и `GameFactory`).

- **`Rendering/`**
  - `RuntimeMaterialFactory` — создаёт цветные материалы для примитивов,
    клонируя один материал-ассет (`Resources/Materials/RuntimeLit.mat`),
    вместо `Shader.Find(...) + new Material(shader)`. Подробнее — в разделе
    "Технические детали" ниже, почему это важно для скорости билда.

- **`Player/`**
  - `PlayerMovement` — движение персонажа (`CharacterController`, WASD,
    гравитация, спринт по `Shift`). Ничего не знает о камере; за то, можно
    ли сейчас бежать, спрашивает `PlayerStamina`.
  - `PlayerCameraController` — отдельный класс для управления камерой:
    поворот камеры по мыши (pitch) и поворот тела игрока (yaw).
  - `PlayerStamina` — **здесь находится логика стамины**: хранит дробное
    значение `0..1`, тратит его на бег (полностью опустошается за
    `sprintDuration = 3` сек. непрерывного бега) и восстанавливает, когда
    игрок не бежит (полностью заполняется за `rechargeDuration = 5` сек.).
    Бег разрешён, только если стамина больше нуля, есть входное движение и
    нет активной блокировки: как только стамина опустошается до нуля,
    выставляется блокировка (`_isLocked`), и бег остаётся недоступен, пока
    стамина не наберётся обратно **полностью** до `1` — небольшого запаса
    "чуть-чуть восстановилось" недостаточно, чтобы побежать снова. Событие
    `StaminaChanged` слушает `UIManager` для обновления полосы в UI.

- **`Collectibles/`** — **здесь находится логика сбора бриллиантов**.
  - `Diamond` — поведение одного бриллианта: вращение/покачивание для
    заметности, обработка `OnTriggerEnter` с игроком, самоуничтожение.
  - `DiamondCollector` — счётчик: сколько всего бриллиантов и сколько
    собрано, события `CountChanged` / `AllDiamondsCollected`. Не знает
    ни о UI, ни об игроке напрямую.

- **`Enemies/`** — **здесь находится логика врагов**.
  - `EnemyAI` — конечный автомат `Patrol / Chase` поверх `NavMeshAgent`
    (NavMesh печётся во время выполнения из сгенерированной геометрии
    лабиринта). Если игрок ближе радиуса обнаружения — преследование,
    если дальше радиуса потери — возврат к патрулю. Поимка игрока
    определяется физическим триггер-коллайдером (`OnTriggerEnter`,
    сравнение по тегу `Player`), а не дистанцией — сравнивать
    `transform.position` игрока (у ног) и врага (центр капсулы, смещённый
    `NavMeshAgent.baseOffset`) не имеет смысла, они никогда не сблизятся
    достаточно. При касании вызывает переданный колбэк
    (`GameSession.ReportDefeat`) и останавливает `NavMeshAgent`.

- **`Interactables/`**
  - `ExitZone` — триггер зоны выхода; засчитывает победу через
    `GameSession.ReportVictory()`, только если `DiamondCollector.AllCollected`.

- **`Factories/`**
  - `IGameFactory` / `GameFactory` — фабрика игровых объектов, читает
    `GameSession`/`DiamondCollector` из `ServiceLocator` (см. выше).
  - `DiamondFactory`, `EnemyFactory` — низкоуровневые статические фабрики:
    собирают полностью настроенный GameObject (примитивы + компоненты +
    материалы) для одного бриллианта или врага. Используются `GameFactory`.

- **`UI/`**
  - `IUIFactory` / `UIFactory` — фабрика UI, читает `GameSession`/
    `DiamondCollector`/`PlayerStamina` из `ServiceLocator` и строит иерархию
    UI (Canvas, HUD-счётчик, полоса стамины, панели победы/поражения, кнопки
    Restart) из примитивов uGUI. Полоса стамины — это `Image` с
    `type = Filled`, `fillMethod = Horizontal` и процедурным белым спрайтом
    (`Sprite.Create(Texture2D.whiteTexture, ...)` — `Image` без спрайта
    игнорирует `fillAmount` и всегда рисует полностью залитый прямоугольник);
    фон — отдельный `Image` под ней того же размера.
  - `UIManager` — единственный класс, который подписывается на события
    `DiamondCollector`, `PlayerStamina` и `GameSession` и обновляет UI (в
    т.ч. `staminaFillImage.fillAmount = fraction`). Не содержит игровых
    правил, только реакцию на события.

### Поток данных

`GameEntryPoint` создаёт `GameSession` и `DiamondCollector` один раз,
регистрирует их вместе с `IGameFactory`/`IUIFactory` в `ServiceLocator`, а
дальше сами фабрики достают нужные сервисы оттуда. Конечные игровые объекты
(`Diamond`, `EnemyAI`, `ExitZone`, `UIManager`) по-прежнему получают ссылки
на конкретные зависимости явно через `Initialize(...)`, а не через
`ServiceLocator` напрямую — это оставляет `ServiceLocator` только на уровне
"составления уровня" (`GameEntryPoint` и фабрики), не размазывая его по всей
игровой логике. Поиска объектов по имени/тегу в рантайме нет (кроме тега
`Player`, который используется для проверки триггеров).

## Технические детали

- Unity 6000.2.11f1, Universal Render Pipeline.
- Вертикальная синхронизация включена в коде: `QualitySettings.vSyncCount = 1;`
  в `GameEntryPoint.Awake()` (кадр ждёт один V-blank монитора).
- Управление реализовано через новый **Input System** (`Keyboard.current`,
  `Mouse.current`), т.к. в проекте `Active Input Handling` = *Input System
  Package (New)*.
- Патрулирование и преследование врагов используют `NavMeshAgent` и
  `NavMeshSurface` (пакет `com.unity.ai.navigation`) — NavMesh строится
  во время выполнения (`NavMeshSurface.BuildNavMesh()`) сразу после
  генерации геометрии лабиринта.
- UI собран на примитивах uGUI (`Text`, `Image`, `Button`) без TextMeshPro,
  чтобы не требовать импорта TMP Essentials.
- Все игровые параметры (размер лабиринта, число бриллиантов/врагов,
  seed) настраиваются в инспекторе на объекте `GameEntryPoint` в сцене.

### Материалы и билд (важный нюанс)

Все материалы в игре — процедурные (пол, стены, бриллианты, враги, выход),
поэтому в первой версии они создавались через
`new Material(Shader.Find("Universal Render Pipeline/Lit"))`. Это ломается
в двух местах:

1. **В билде `Shader.Find` может вернуть `null`.** Редактор видит все шейдеры
   проекта, а в собранный билд Unity включает только шейдеры, на которые
   есть явная ссылка (материал-ассет на диске, Always Included Shaders и
   т.п.). Раз ни один `.mat`-файл на URP `Lit` не ссылался, шейдер не
   попадал в билд, `Shader.Find` возвращал `null`, и `GameEntryPoint.Awake()`
   падал с `ArgumentNullException` на первом кадре — билд запускался, но
   уровень не собирался.
2. **Если просто добавить шейдер в Always Included Shaders — билд станет
   очень долгим.** Без материала-ассета, по которому видно, какие именно
   keyword-комбинации реально используются, Unity не может сузить набор
   вариантов и компилирует широкий "дефолтный" набор — для URP `Lit` это
   десятки тысяч вариантов только для прохода `ForwardLit`.

Решение — `RuntimeMaterialFactory` (`Rendering/RuntimeMaterialFactory.cs`)
клонирует один реальный материал-ассет `Assets/Resources/Materials/RuntimeLit.mat`
(лежит в `Resources/`, поэтому гарантированно попадает в билд) вместо вызова
`Shader.Find`. У этого материала keyword `_EMISSION` включён по умолчанию, так
что все клонированные материалы (светящиеся и обычные — просто с
`_EmissionColor` в чёрном) используют один и тот же вариант шейдера. Билд-тайм
стриппинг видит один материал с одним конкретным набором keyword'ов и
компилирует ровно то, что нужно, вместо перебора всего пространства вариантов.
